== 📖 Objectif du module
Ce dossier contient le serveur back-end principal du portail de réservation Synchrotron SOLEIL, développé avec le framework Python **Django** et **Django REST Framework (DRF)**.

**Ses responsabilités principales :**
* 🗄️ **Base de données** : Gestion relationnelle via PostgreSQL pour centraliser les profils utilisateurs, les experts et le planning des créneaux.
* 🔒 **Sécurité, Authentification & RGPD** : Gestion des sessions sécurisées par JWT via `dj-rest-auth` (avec stockage en cookie HttpOnly), authentification OAuth2 (Google, GitHub, LinkedIn), et gestion sécurisée des profils incluant le droit à l'oubli (suppression définitive du compte).
* 📧 **Notifications SMTP** : Déclenchement et envoi automatisé d'e-mails transactionnels (Création de compte, Confirmation de réservation, Annulation, Réinitialisation de mot de passe).
* ⚙️ **Traitements Asynchrones & Tâches Planifiées** : Utilisation du broker **Redis** et des *workers* **Celery** pour déléguer les processus en arrière-plan et exécuter des tâches planifiées (CRON), comme l'envoi d'e-mails de rappel automatiques.
* 🧠 **Moteur NLP (IA)** : Intégration de l'API Google Gemini 2.5 Flash pour analyser les requêtes en langage naturel et structurer les critères de filtrage.
* 🛡️ **Logique Métier & Tableaux de bord** : Algorithmes garantissant qu'un créneau est verrouillé dès sa réservation, et isolation des données assurant qu'un patient ou un expert n'accède qu'à ses propres informations (via des tableaux de bord et vues dédiés).

== 🏗️ Architecture et Fichiers Clés
Voici le détail des fichiers que nous avons créés et configurés pour construire cette architecture orientée API REST :

* `core/settings.py` : Cœur de la configuration. Contient la connexion à PostgreSQL, les variables SMTP, l'intégration des middlewares CORS, la configuration `dj-rest-auth`, ainsi que les variables de connexion au broker **Celery / Redis**.
* `core/celery.py` : Configuration de l'application Celery et de son *Scheduler* (Celery Beat) pour la planification des tâches quotidiennes.
* `core/__init__.py` : Modifié pour garantir le chargement automatique de l'application Celery au lancement de Django.
* `core/urls.py` : Point d'entrée du routage Django. Expose les endpoints de l'API métier (`/api/`) et intègre les routes d'authentification classiques et OAuth.
* `core/auth_views.py` : Connecteurs configurant les adaptateurs OAuth (Google, GitHub, LinkedIn) avec leurs URLs de redirection dynamiques pointant vers le front-end React.
* `booking/models.py` : Définition de la structure de la base de données. Contient un modèle `User` personnalisé (sans champ username), et les modèles `Expert`, `TimeSlot` et `Appointment`.
* `booking/serializers.py` : Couche de transformation JSON. Intègre un `UserSerializer` strict et inclut dynamiquement les informations des patients pour les créneaux réservés des experts.
* `booking/views.py` : Contrôleurs de l'API (ViewSets). Gèrent l'isolation multi-tenant, déclenchent l'envoi direct d'e-mails transactionnels croisés (Expert <-> Patient) et incluent le `ExpertDashboardViewSet` qui restreint rigoureusement l'accès au planning professionnel.
* `booking/tasks.py` : Scripts exécutés en arrière-plan par les *workers* Celery (ex: `envoyer_rappels_rdv` pour alerter les patients à J-1 de leur rendez-vous).
* `booking/signals.py` : Écouteurs d'événements asynchrones natifs à Django (création de compte, mot de passe).
* `booking/ai_service.py` : Interface avec le modèle Google Gemini 2.5 Flash.
* `booking/tests.py` : Suite exhaustive de tests automatisés avec Pytest validant la sécurité de l'API : respect de l'isolation des données, conformité RGPD, blocage de sécurité sur l'espace expert (`TestExpertDashboardSecurity`) et validation du déclenchement temporel des tâches Celery avec mock SMTP (`TestCeleryRappels`).
* `pytest.ini` : Fichier de configuration minimal permettant à Pytest de s'amorcer.

== 🚀 Lancement et Arrêt du serveur

L'environnement étant intégralement conteneurisé, toutes les opérations de cycle de vie s'effectuent via Docker depuis la racine du projet.

=== Lancement de l'environnement complet
Placez-vous à la racine du projet (au niveau du fichier `docker-compose.yml`) et exécutez la commande de construction et de démarrage :
[source,bash]
----
docker compose up --build
----
Cette commande lancera simultanément la base de données, le serveur Django (sur **http://localhost:8000/**), ainsi que les conteneurs `redis`, `celery_worker` et `celery_beat` nécessaires aux tâches en arrière-plan.

=== Exécution des tests automatisés (Pytest)
Pour valider l'intégrité de la logique métier et de la sécurité, exécutez la suite de tests à l'intérieur du conteneur backend actif :
[source,bash]
----
docker compose exec backend pytest -v
----

=== Déclenchement manuel des tâches (Celery)
Pour tester immédiatement l'envoi des rappels de rendez-vous asynchrones sans attendre l'heure planifiée par le CRON, exécutez la tâche directement dans le *shell* du conteneur :
[source,bash]
----
docker compose exec backend python manage.py shell -c "from booking.tasks import envoyer_rappels_rdv; print(envoyer_rappels_rdv())"
----

=== Arrêt du serveur
Pour stopper proprement le serveur backend, les workers Celery et libérer les ports de la machine hôte, utilisez la commande suivante depuis la racine du projet :
[source,bash]
----
docker compose down
----
_Note : Si vous souhaitez également effacer la base de données PostgreSQL pour purger toutes les réservations et les utilisateurs, ajoutez l'argument `-v` (`docker compose down -v`)._
